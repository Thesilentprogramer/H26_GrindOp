# CLAUDE.md

Instructions for AI coding assistants working in this repo. Read this and `PRD.md` before writing code.

## What this project is

A CLI developer tool (Hacktoberfest Hack Day Mumbai, **Track 1: Gemma 4 Dependency Resilience**) that analyses a Python repository and produces a **Dependency Exit Capsule** for every at-risk dependency.

Pipeline: `scan -> trace -> ai_migrate -> verify -> capsule`

Target repo for judging: https://github.com/rishrek/LinkWatch (Python 3.12 and 3.13 only, **not 3.14**).

## Non-negotiable rules

1. **Observed vs AI-suggested must never mix.** Every datum in the capsule lives under either `observed` (produced by our code: parsing, HTTP metadata, AST, executed commands) or `ai_suggested` (produced by Gemma 4). Never copy a model claim into `observed`. If a model claim is later checked by code, store the check result under `observed.verification` and link it to the claim by id.
2. **The model never executes anything.** Gemma proposes; our code executes. No shell, no file writes, no network calls driven by model output without validation.
3. **Never modify the target repo in place.** Copy it to a temp dir and work there. Applying AI-suggested patches happens only in the copy.
4. **No paid APIs, no paid cloud.** Use the free Gemma 4 access from the MLH quickstart, or a local model. Do not add any other hosted LLM provider.
5. **No secrets in git.** API keys come from environment variables only. Keep `.env` in `.gitignore`; commit `.env.example`.
6. **Analysis is dynamic.** No hardcoded dependency lists, canned LinkWatch answers, or pre-generated capsules inside the tool. Sample outputs in `examples/` must be produced by running the tool.
7. **Be honest about gaps.** If something is not executed or could not be verified, record it with a reason (`status: "not_executed"`, `reason: "..."`). Never fabricate results or present mock-ups as working.
8. **Security vulnerabilities in LinkWatch are out of scope** (zero points per the handbook). Do not spend time on them.

## Environment

- Python **3.12 or 3.13**. Target repos are tested on these only.
- Package/venv management: `uv` (fallback: `python -m venv` + `pip`).
- Tests: `pytest`.
- Config via env vars:
  - `LLM_BASE_URL` - Gemma 4 endpoint (OpenAI-compatible if the provider supports it; confirm in MLH docs)
  - `LLM_API_KEY`
  - `LLM_MODEL` - exact Gemma 4 model id (confirm in MLH docs; do not guess)
  - `GITHUB_TOKEN` - optional, raises GitHub API rate limit

## Commands

```bash
uv venv --python 3.12 && source .venv/bin/activate
uv pip install -e ".[dev]"

pytest                                        # unit tests for this tool
python -m exitcapsule <repo-url-or-path>      # run full pipeline
python -m exitcapsule <repo> --stage scan     # run a single stage
python -m exitcapsule <repo> --no-verify      # skip execution stage
ruff check . && ruff format .
```

## Layout

```
exitcapsule/
  cli.py        # argparse entry point, stage orchestration
  models.py     # dataclasses / pydantic models = capsule schema (source of truth)
  scanner.py    # parse deps, fetch PyPI + GitHub metadata, risk scoring
  tracer.py     # AST import and call-site tracing
  llm.py        # thin Gemma 4 client, retries, JSON validation
  migrate.py    # builds prompts from evidence, validates model output
  verify.py     # temp copy, venvs, install, test runs, API-mapping checks
  report.py     # capsule JSON + Markdown (+ optional HTML) rendering
prompts/        # versioned prompt templates (visible to judges)
tests/          # unit tests with fixtures, no network
examples/       # capsules generated by running the tool on LinkWatch
```

`models.py` is the contract between modules. Change it only with team agreement, because every module depends on it.

## Coding conventions

- Type hints everywhere; small pure functions; one responsibility per module.
- Each stage takes and returns the typed models, and can run alone from its JSON output.
- Network calls: timeouts on every request, retries with backoff, cache responses on disk (`.cache/`) so reruns are fast and offline-friendly.
- Subprocesses: always set `timeout`, capture stdout and stderr, record the exact command and exit code in the capsule.
- Validate all LLM output against the schema. Retry up to 2 times on invalid JSON, then record the failure (`ai_suggested.status: "failed"`) instead of crashing the run.
- Log what happened; do not swallow exceptions silently.
- Prompts live in `prompts/` as files, not inline strings.
- Keep dependencies of this tool minimal and permissively licensed; list them in the README.

## Git rules (judged)

- Use Git only, small meaningful commits, every team member commits.
- Commit messages: imperative, scoped (`scanner: parse pyproject.toml deps`).
- Never rewrite history or fake commit dates.
- Final repo name: `H26_TeamName_ProjectName`, forked from the organizers' starter, with an OSI license (MIT or Apache-2.0).

## Definition of done for any feature

- Runs against LinkWatch without manual input beyond the repo URL or path.
- Output validates against the capsule schema.
- AI vs observed separation preserved.
- Failure modes handled and reported, not hidden.
- Short note added to the README if it changes setup, usage, or limitations.

## AI-assistant etiquette

- Handbook says heavy AI use must be avoided and outputs verified. Review and understand everything you generate; keep diffs small.
- If you are unsure of a Gemma 4 model id, endpoint, license term, or a LinkWatch fact, say so and leave a `TODO(verify)` rather than inventing it.
- Do not add features outside `PRD.md` scope. Anything in "Non-goals" stays out.
